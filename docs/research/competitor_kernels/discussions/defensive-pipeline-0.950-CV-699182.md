I wanted to share a few findings from building a submission for this competition, focusing on the parts that *didn't* work the way I expected. The final submission was a calibrated blend of LightGBM, CatBoost, and RealMLP at CV AUC 0.95019, with the original F1 dataset folded in. The leaderboard position isn't the point of this post, the point is three diagnostics that I think generalize beyond this competition.

## The data has a structural quirk worth exploiting

Before any modeling, I checked how the train/test split was constructed. The split is stratified-random across all four years (2022–2025), not temporal, so the test set draws from the same race-driver distribution as train. Specifically: **96.32% of test (Year, Race, Driver) units have at least one lap in train**.

That's the central feature-engineering opportunity. For each test row at, say, (Year=2024, Race=Qatar, Driver=D109, Stint=2), you can look up *other* laps from the same driver-race-stint in the training set and compute aggregates: max tire age reached in this stint, slope of lap times, whether `PitStop=1` was already observed. These features are computed from train rows only and merged onto both train and test by the unit/stint key. They're leakage-resistant because the test set was generated by random row-sampling within units, not by holding out whole races.

Adding these features lifted LightGBM CV AUC from ~0.91 (base features only) to 0.947 (with stint aggregates). Larger lift than any tuning step gave me later.

## 2023 is structurally anomalous and your CV needs to know

The pit rate per year in the synthetic training data is wildly uneven:

| Year | Pit rate |
|---|---|
| 2022 | 26.7% |
| 2023 | **0.96%** |
| 2024 | 29.5% |
| 2025 | 28.4% |

The 2023 anomaly is preserved from the original dataset (where 2023 sits at 3.08% vs ~32% for other years), so it's not a synthesis artifact. Whatever caused it in the real data, sprint-format weekends, regulation changes, fewer mandatory stops, the synthetic data inherits the regime. Additionally, this anomaly may have been an intentional artifact in the data.

This matters operationally because **you need a per-year CV AUC breakdown, not just an overall score**. My tuned LightGBM had overall CV AUC 0.947 but per-year:

| Year | CV AUC |
|---|---|
| 2022 | 0.909 |
| 2023 | 0.934 |
| 2024 | 0.924 |
| 2025 | 0.924 |

2023 is actually the *highest* AUC year, which is the smoking gun that the model is using Year as a regime indicator (predict near zero whenever Year=2023). That's legitimate signal because 2023 really does have a different base rate, but if you only look at overall AUC you miss that one year is being predicted by a single feature.

If you submit a model that doesn't handle 2023's regime properly, your overall AUC can look fine while one slice quietly collapses. Worth tracking.

## Blending three GBDTs is not actually blending

This is the one I got wrong and want to share...

My first ensemble pass used LightGBM (tuned, 0.947), XGBoost (default, 0.943), and CatBoost (0.950). All three are gradient-boosted decision trees, all trained on the same features. I expected rank-averaging them to lift CV AUC by the usual +0.003 to +0.005.

It didn't. Here's what came back:

- Rank-average of all three: **0.94845** (worse than CatBoost alone)
- Logistic stacking of all three: 0.94977 (also worse than CatBoost alone)
- Stack coefficient on XGBoost: **−1.41**

That negative coefficient is the diagnostic. The stacker is saying "when XGBoost disagrees with the other two, trust the disagreement *backward*." That happens when a model's errors are correlated with the other models' errors but its signal isn't adding anything new. XGBoost was effectively a noisier copy of LightGBM and the pairwise Spearman correlations confirm:

|  | LGBM | XGB | CAT |
|---|---|---|---|
| LGBM | 1.000 | 0.981 | 0.967 |
| XGB | 0.981 | 1.000 | 0.957 |
| CAT | 0.967 | 0.957 | 1.000 |

ρ(LGBM, XGB) = 0.981 is too high. Two models that close to each other don't add diversity to a blend; they amplify whatever shared errors they have.

The fix wasn't to tune XGBoost harder. Better tuning would have moved ρ from 0.981 to maybe 0.978 (not enough). The fix was to drop XGBoost and add a model from a genuinely different family.

I used **RealMLP** from the [PyTabKit library](https://github.com/dholzmueller/pytabkit) (Holzmüller, Grinsztajn, Steinwart, NeurIPS 2024). It's a feed-forward neural network with meta-tuned defaults — no per-dataset HPO required. The new correlations:

| Pair | ρ |
|---|---|
| (LGBM, CAT) | 0.967 |
| (LGBM, RealMLP) | <0.96 |
| (CAT, RealMLP) | <0.96 |

The blend of LGBM + CAT + RealMLP (without XGBoost) cleared the +0.002 acceptance gate I'd set against CatBoost alone.

The lesson, which I'd seen written before but didn't internalize until I'd done it: **ensembling three implementations of the same algorithm family is not the same as ensembling three algorithms.** Gradient boosting on a fixed feature set converges to similar functions regardless of whether the implementation is LightGBM, XGBoost, CatBoost, or HistGradientBoosting. The ensemble benefit comes from architectural diversity, not implementation diversity.

## Rank-averaging breaks per-year calibration sanity checks

One more small thing that surprised me.

Rank-averaging is the standard trick for AUC-metric blending: convert each model's predictions to ranks (1 to N), average the ranks, divide by N. AUC depends only on ranking, so this preserves the AUC of each model while reducing noise across the ensemble.

What I didn't think about until it backfired: **the output of rank-averaging is uniform on [0, 1] by construction**. Overall mean ≈ 0.5. So if your submission verification includes a per-year mean sanity check (which mine did —> "2023 mean should be ≈ 0.03 like the training base rate, others should be ≈ 0.28"), rank-averaged predictions will fail that check even though the ranking is correct.

Fix: isotonic regression on the OOF predictions, then apply the calibrator to the test predictions. Isotonic is monotonic, so it preserves AUC exactly, but it pulls the values back onto a calibrated probability scale. After calibration, my per-year means matched the training base rates and the regime check passed.

This is also a real benefit if the score is going to be used downstream for anything that depends on probability calibration (e.g., expected-value calculations, threshold-based decisions). For pure AUC optimization it doesn't change the score, but it makes the predictions usable.

## What didn't matter

A few things I tried or considered that turned out to be no-ops or worse:

- **Adding more GBDT variants** (HistGradientBoosting, different LightGBM seeds). Same correlation problem as XGBoost —> no diversity gain.
- **Heavy resampling (SMOTE, undersampling)**. AUC is threshold-invariant, so class balance manipulation doesn't help. Can hurt calibration.
- **Threshold tuning.** Same reason —> AUC doesn't care.
- **Time-based splits (train on 2022–24, test on 2025).** The actual competition split is stratified-random across all years. A temporal split creates covariate shift you wouldn't see at evaluation time.

## What I'd try next if I were chasing higher

CatBoost was my strongest single model and the only one I didn't tune with Optuna (LightGBM tuning gave +0.0033, CatBoost was used at near-defaults). Probably +0.001 to +0.003 left on the table there.

Within-stint feature variants I didn't engineer: rolling variance of lap times, change in position trajectory within a stint, gap-to-leader if it were available.

Pseudo-labeling on high-confidence test predictions (probability > 0.95 or < 0.05) is a standard trick that probably adds +0.001 to +0.003 but carries confirmation-bias risk.

## Stack and tools
- Python 3.11
- LightGBM 4.x, XGBoost 2.x, CatBoost 1.2, PyTabKit (RealMLP)
- Stratified 5-fold CV with seed=42, identical splits across all base models
- Optuna for LightGBM tuning, defaults for CatBoost and RealMLP
- Isotonic regression for blend calibration
- pytest suite for submission verification (row count, id alignment, value range, per-year regime sanity)

Happy to answer questions about any of the diagnostics. The XGBoost stack-coefficient finding is the one I'd most want to know about before doing another ensemble.
